# 对照实验：同一模型、同一审查任务，不用工作流 vs 用工作流

2026-11-18 · DSH 0.2.2-rc.4 headless · `workbuddy/deepseek-v4.1-flash` · 每组 2 次

## 任务

一个埋了标准答案的小仓库（`tests/eval/repo.mjs`）：12 个 TypeScript 模块，约 250 行。

- **14 个埋下的 bug**，难度分层：从“没有比较函数的 `sort()`”到“`expiresAt === now` 算不算过期”这类边界问题。
- **5 个诱饵**：看起来像 bug、其实是对的代码，例如 `i <= length - 1`、`new Date(y, m, 0)`。报出诱饵就算误报。

两组用同一个提示词：“审查 src/ 找出所有明确的 bug，只读，末尾给 JSON 清单”。工作组只在前面多一句“用工作流完成这个任务”。

所有模型请求都经过一个本地计数代理，所以两组的 token 都是精确值，包括主代理和每个子代理。

## 结果

| 组 | 埋下的 bug 找到 | 误报诱饵 | 额外发现（不在答案里） | 耗时 | tokens（输入+输出） | 模型请求 |
|---|---|---|---|---|---|---|
| 普通对话 #1 | 10/14 | 0/5 | 0 | 76 s | 190K | 20 |
| 普通对话 #2 | 11/14 | 0/5 | 0 | 91 s | 98K | 9 |
| 工作流 #1 | 11/14 | 0/5 | 3 | 470 s* | 2.33M | 198 |
| 工作流 #2 | 11/14 | 0/5 | 1 | 364 s* | 2.61M | 217 |

\* 沙箱的 shell 调用限时约 170 秒，所以工作流组被切成 3 段跑：每段结束时 Host 退出，下一段用 `--session-id` 续跑。每次中断都会让在途的子代理把当前任务重做一遍，因此工作流组的耗时和 token 都比不中断时偏高。普通对话组每次都在一段内跑完。

两次工作流运行分别用了 30 个和 29 个子代理。

**额外发现**都是真实存在、但我没有埋的边界问题：

- `groupBy` 遇到 `constructor` 之类的键时会取到原型链上的值，随后 `push` 抛异常；
- `unique` 会把 `NaN` 全部丢掉；
- 模板 `{{constructor}}` 会渲染出函数源码；
- `isHttps` 对大小写敏感。

## 结论

在这个规模（一个上下文轻松装下的 12 个文件）上：

- **找埋下的 bug，工作流没有优势。** 两组都稳定在 10–11/14，漏的也基本是同几个（`retry` 最后一次失败后多睡一次、过期边界、`Bearer` 解析）。
- **两组都没有误报诱饵。** 这个模型单独审查时已经足够谨慎。
- **工作流多找到的是“没被要求、但真实存在”的边界问题**，平均每次 2 个；普通对话一个都没有。逐文件的独立审查加上独立复核，体现在覆盖面上，而不是命中率上。
- **代价是约 15–25 倍的 token、4–5 倍的时间**（时间有一部分来自分段中断）。

所以在小任务上，工作流主要是开销。它的价值要到上下文装不下、或者需要“每一项都被看过”的保证时才可能显现。这次没有测到这个分界点；下一步应当在大约 10 倍规模（上百个文件）上重复同样的对照。

## 复现

```sh
npm run build
node tests/eval/ab.mjs start plain    /tmp/ab/plain-1
node tests/eval/ab.mjs start workflow /tmp/ab/wf-1
node tests/eval/ab.mjs continue /tmp/ab/wf-1        # 运行被时间限制切断时重复
node tests/eval/ab.mjs score /tmp/ab/plain-1 /tmp/ab/wf-1
```

网关、密钥和模型从 `.env` 读取。在不限时的终端里运行时，可以把 `DWF_SEGMENT_MS` 调大，一段跑完。
